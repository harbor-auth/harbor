# NOT PRODUCTION READY

**Status as of 2026-08-08.** The system is deployed and working end to end. It
is **not** ready to carry real users, and this file says exactly why.

Read it before pointing anything at this deployment that you would be sorry to
lose.

## The blockers, in the order they will hurt you

### 1. A personal OAuth token is the registry credential — HIGH

`ghcr-pull` on both clusters holds a token that also carries
**`admin:enterprise`, `repo` and `workflow`**. Anything that can read a Secret
on either node can take over the enterprise.

*Fix:* a fine-grained PAT limited to `read:packages`, or make the packages
public. One `kubectl create secret docker-registry --dry-run | kubectl apply`;
nothing else changes.

### 2. OpenBao is one pod with manual unseal, and the shares are on a laptop — HIGH

A node reboot seals it and **everything signing-related stops**. This already
happened, unattended, at 04:30 on a Saturday, and was silent for three hours.

Worse: the unseal shares are supposed to live with five separate custodians.
They are in fact all together in
`~/.harbor/openbao/openbao-init-2026-08-02.json` on one machine — which is how
I was able to unseal it single-handedly. That file also contains the **root
token**. A 3-of-5 Shamir scheme where one laptop holds all five shares is a
1-of-1 scheme with extra steps.

*Fix:* distribute the shares for real, or configure auto-unseal against a KMS
the cluster can reach. Then destroy the combined file. Alert on `sealed=true`
either way.

**Blast radius grows** once the DEK→OpenBao migration lands: today a sealed
vault blocks harbor-hot's startup; afterwards it blocks *every login*. Do the
availability work first.

### 3. Two production credentials were generated by an assistant — HIGH

Both are load-bearing, both sit in a scratchpad at mode 0600, neither is in git,
and **neither survives a cluster rebuild**:

- `cloud-service-auth.key.pem` — signs the provisioner's assertions; its public
  half is harbor-mgmt's trust anchor.
- `sso-subject-hmac.key` — `SSO_SUBJECT_HMAC_KEY`. Rotating it orphans every
  federated identity (free today at zero users; not free later).

*Fix:* regenerate both yourself and move them into the sealed-secret flow.

### 4. No offsite backups — HIGH

Backups run daily, verified, retained 14 — **on the same physical machine as the
database**. The two R2 CronJobs are deployed but suspended, waiting on
credentials. A host failure loses the data and the backups together.

### 5. Disaster recovery is unproven, and one landmine was already found — MEDIUM

`harbor-postgresql-auth.password` did not match the live role password. It hid
because `POSTGRES_PASSWORD_FILE` is only read at initdb, *and* `pg_hba.conf`
trusts loopback — so no in-pod credential test can detect it. Rebuilding from
git would have produced a database no service could log into.

Corrected, but nothing has ever rehearsed a restore. Untested backups are
hope, not recovery.

### 6. `harborauth.com` and `demo.harborauth.com` do not resolve — MEDIUM

**Order matters:** DNS first, then restore harbor-cloud's auto-sync. Doing it
the other way applies a Certificate naming two hosts that do not resolve,
cert-manager opens a permanently failing ACME order, and it burns Let's Encrypt
rate limit against the whole account.

### 7. harbor-cloud is not self-healing — MEDIUM

Auto-sync is deliberately off (see 6). Every change is applied by hand;
nothing drifts back. `linkerd-crds` was deleted as a stale Application that
never installed anything.

### 8. mTLS between services is deferred — MEDIUM

Linkerd pinned chart `2.16.0`, which does not exist — that is the *release*
version; the charts version independently. It never installed, at any point.
Removing it is what finally let this cluster be GitOps-managed at all.

### 9. Single node, no HA — MEDIUM

Both clusters are one k3s node each on one Hetzner host. Postgres, Redis and
OpenBao are single pods. `etcd-snapshot-*` config is inert because k3s here runs
on SQLite — the config advertises state backups that do not exist.

### 10. An org-wide GitHub setting was loosened — LOW

`deploy_keys_enabled_for_repositories` is now `true` on the org and **must stay
on** — disabling it does not merely block new keys, it deactivates existing
ones. Verified both directions.

### 11. Residue — LOW

One inert probe user (`b8d5f93c…`) from verifying the SSO flow. No credential,
no federated identity, no session. Left in place because the only remaining
reference is an `audit_events` row, and deleting users by hand to tidy a count
is the wrong instinct in an auth system. Use the product's erasure path.

## The pattern worth internalising

Five separate bugs shipped, and **every one passed every check in the repo**:

1. the devshell's `migrate` binary panicked before `main()` — nixpkgs builds it
   with a Snowflake driver whose `init` aborts;
2. `admin-ui` was deployed from an image that had never been published — its
   build ran with `push: false`;
3. a kustomize overlay silently *deleted* the provisioner's key volume, because
   a JSON-Patch `add` on an array replaces it;
4. the relay named a ServiceAccount nothing created;
5. the backup job could never reach the database — cross-namespace Secret and
   NetworkPolicy.

The shared shape: **the repo asserted against an intermediate artifact — base
manifests, a correctly-shaped tag, a chart template — while the thing that
actually runs is produced later.** Each fix now has a test that renders or
executes the real artifact, and each was verified by breaking it deliberately
and watching the test fail.

Assume more of these exist. The audit worth doing is: for every assertion, ask
what it would still pass with.
